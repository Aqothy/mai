# Centering, streaming consistency and animation removal

Source: `1aa5220` (geometry/alignment), then `217e488` (plain text). macOS 27.0, Xcode MCP builds. iOS 27 simulator retains deployment target 18.6.

## Reproduced defects and changes

1. **List alignment:** a normal synthetic List opened centered. The benchmark's `scrollRowToVisible` follow-up then overwrote `NSClipView.bounds.origin.x` with zero. The actual horizontal origin was −280 points, accounting for SwiftUI's sidebar layout. This reproduces the user's screenshot. Vertical benchmark jumps now preserve x and reject runs that change it. `list-before.png` and `list-after.png` show the reproduction and correction, captured from the original `a5340d8` and intermediate geometry fix respectively. Three successive sweep anchors logged `x=-280.0 preservedX=true`.
2. **Working-row jump:** live row heights changed synchronously, but the scroll controller corrected the bottom position after a task yield. The new regression reproduced a working-row position of 209 instead of 179 points on the first growth before the fix, and larger displacements on subsequent growth. Geometry now calls the scroll controller synchronously at its commit boundary, and Core Animation groups row frames, extent and scroll correction without implicit animation. List retains its deferred AppKit-managed layout handling. Reading anchors also update when row heights redistribute without changing the document's total height.
3. **Plain streaming:** removed the reveal state machine, per-character renderer and timed fading from prose, quotes and code. Removed the working symbol pulse and phrase transition. Markdown parsing, stable-block reuse, selection and final-source handling remain. `ChatStreamingTextReveal.swift` contains only a comment because the existing Xcode project explicitly references the file; no animation implementation remains and the project was not edited.

## Browser blanking and mobile conclusions

The installed `/Applications/ChatGPT.app` version 26.915.31029 (9771), bundle ID `com.openai.codex`, contains Electron resources and `app.asar`. Read-only inspection of bundled `thread-virtualizer`, `virtualized-turn-list`, `thread-scroll-layout` and `conversation-blocks` assets found measured turn heights, a rendered range with overscan, scroll anchoring and `content-visibility:auto` with intrinsic-size estimates. The virtualized turn wrapper overrides its mounted content to visible. No inspected code established an intentional whole-chat blanking mode at a particular scroll speed. No account files were inspected or application files modified; no proprietary implementation was copied into mai.

Chromium can continue compositor scrolling while newly exposed content is not ready, producing stale or blank/checkerboard regions. Virtualized app content may also arrive late. This makes the reported symptom plausible but does not establish its exact cause in ChatGPT. See [Chromium's rendering critical path](https://www.chromium.org/developers/the-rendering-critical-path/). Intentionally hiding readable content is not part of this change. Keep mounted content, prepare nearby rows, and defer nonessential work; assess visual completeness and latency alongside pacing.

A steady 60 Hz cadence has a 16.7 ms interval; 120 Hz has 8.3 ms. Uneven frame intervals can feel worse than a lower steady rate. The earlier desktop List results were not a fixed 60 Hz cap, and their misalignment additionally invalidates a final controlled comparison. Desktop results do not establish iOS List performance. A custom UICollectionView provides sizing/reuse control but is not intrinsically a frame-rate upgrade.

Use a physical ProMotion device for the 120 Hz decision, and a physical 60 Hz device for that supported baseline. Simulator runs can validate behavior and reveal expensive work, but do not represent phone CPU/GPU, thermals or refresh scheduling. The user deferred connecting the iPhone 14. Apple's [responsiveness guidance](https://developer.apple.com/documentation/xcode/improving-app-responsiveness) recommends real-device hitch profiling. Its [ProMotion guidance](https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays) explains adaptive refresh and the Info.plist opt-in for custom display-link rates above 60 Hz on iPhone. The current simulator artifact lacks that opt-in; a future benchmark must not misdiagnose this configuration ceiling as List's rendering limit. No project setting was changed.
