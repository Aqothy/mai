# Desktop keyboard QA — September 27, 2026

The normal app reproduced Shift+Return selecting the entire prompt instead of inserting a newline. Typing afterward could replace the draft. The user confirmed that desktop Enter should send and Shift+Enter should add a line.

`PromptComposer` now handles unmodified desktop Return explicitly. An active completion is accepted first; otherwise it invokes Send only when the composer is enabled, can send, and is neither sending nor stopping. It does not invoke Stop. Repeated key-down events are excluded. Caps Lock does not prevent submission. Shift+Return calls the native editor's [insertNewlineIgnoringFieldEditor action](https://developer.apple.com/documentation/appkit/nsstandardkeybindingresponding/insertnewlineignoringfieldeditor(_:)), preserving native selection replacement and Undo. Return is left to the input method when the active editor has marked text; physical input-method validation remains open. iOS does not receive the desktop send binding; modified Return no longer accepts a completion there.

## Evidence

- Actual normal macOS app: Shift+Return followed by `x` produces `QA first line\nx`; Undo restores the original line. Replacing selected `middle` in `café 👩🏽‍💻 middle suffix` with Shift+Return produces `café 👩🏽‍💻 \n suffix`; Undo restores the exact Unicode draft and selection.
- Enter in the normal app reaches Send. The synthetic store deliberately has no daemon connection, so it reports `Not connected to maiD`; dismissing the alert retains the exact draft. Empty-draft Enter produces no alert or edit, and Send remains disabled. The QA draft was cleared and the synthetic app closed.
- `keyboard-send.swift` hosts the actual production composer and sends key events. Its final PASS marker verifies completion Up/Down/Return/Tab/Escape, Unicode native editing, focus release, exactly one Send on Return, no repeated Send from held Return, no Send while unavailable/sending/stopping, recovery when available, and Caps Lock handling. Results are in `keyboard-send-result.json`. The isolated window is not the OS key window, so this harness does not pass native newline or input-method behavior; those have the separate normal-app evidence above.
- Final Xcode MCP builds succeed on macOS and iOS 18.6. The 14 focused completion/draft/annotation regressions pass on each, without failures or skips. Compressed build/test logs and iOS result metadata are retained. No deployment target or generated source changed.

The normal app was necessary because the preview-host window did not route unhandled native Return events normally. The initial app lookup timed out; a name lookup selected an older cached QA app. That app and the leftover snippet host were stopped before selecting the exact current app path and confirming the synthetic transcript. No keyboard pass is based on that mistaken window. `normal-app-observations.json` records selected accessibility observations and the intermediate binary-identity limitation; the fixed launch file copied a stale hash and is deliberately not evidence of an exact executable hash. Final source/evidence hashes are in `manifest.json`.

These results do not pass physical keyboard/input-method combinations, iOS software-keyboard/rotation/long-quote controls, mouse completion selection, accessibility, the complete live-provider matrix, or distribution readiness. They extend the focused [completion QA](../composer-20260927/REPORT.md), not the entire release checklist.
